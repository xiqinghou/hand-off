# 交接目录与命名契约

设备交接和对话交接使用同一套当前入口。目录名固定为项目根目录的 `交接/`；当前文件名固定，不使用“最新、最终、最终版2、当前-新”等版本词。批次、时间和设备信息写入元数据与归档目录，不写入当前文件名。

## 固定目录

```
交接/
├── README.md                 # 唯一入口
├── 校验清单.json              # 当前批次的结构与哈希清单
├── 工作交接/
│   ├── 任务交接.md            # 整体计划、当前/中断任务、下一步
│   ├── 文件导航.md            # 项目结构与阅读顺序
│   ├── 环境与验证.md          # 设备详填；对话简写已有环境与证据
│   ├── 归档索引.md            # 退役文件的原路径、去向与替代关系
│   ├── 接收回执.md            # 接收方填写；首次交出时可注明“尚未接收”
│   └── 归档/<handoff_id>/     # 旧批次和退役执行材料
└── 配置交接/
    ├── README.md              # 配置白名单、恢复步骤和限制
    ├── 文件清单.json           # 设备必需；对话可省，README 注明“不采集”
    ├── codex/                 # 可上传的脱敏最小配置（可选）
    ├── skills/hand-off/       # 可上传的便携 Skill
    └── .codex/                # 可选：含真实 API 密钥，仅本地/U 盘，Git 忽略
        ├── config.toml        # 最小可用配置
        ├── auth.json          # 仅必要 API key，不含 OAuth 登录态（如适用）
        ├── README.md          # 本地恢复说明，无秘密值
        ├── 文件清单.json       # 本地文件哈希，不上传
        └── skills/hand-off/   # 随恢复包携带的 Skill
```

`配置交接/skills/hand-off/` 是随设备交接携带的本 Skill 副本，不属于当前状态文件；不得放置缓存、密钥或父目录副本。

## 当前文件命名规则

| 内容 | 固定文件名 | 规则 |
|---|---|---|
| 唯一入口 | `交接/README.md` | 永远只有一份；正文包含场景、方向、批次和下一步 |
| 计划与任务账本 | `工作交接/任务交接.md` | 同时覆盖整体计划和当前/中断任务，不再拆出并列“任务状态” |
| 文件体系 | `工作交接/文件导航.md` | 只描述路径职责与阅读顺序，不复制规范全文 |
| 环境与证据 | `工作交接/环境与验证.md` | 设备必填；对话按实际情况填写 |
| 归档登记 | `工作交接/归档索引.md` | 记录原路径、归档路径、哈希/状态和替代入口 |
| 接收记录 | `工作交接/接收回执.md` | 接收方追加新环境事实，不覆盖交出方快照 |
| 配置清单 | `配置交接/文件清单.json` | 设备交接必填；不写秘密值 |
| 结构清单 | `校验清单.json` | 脚本生成；不把自身哈希写入自身 |

历史原件可保留原名，但只能位于 `工作交接/归档/<handoff_id>/` 或项目既有历史区，并由 `归档索引.md` 说明。项目规范、源代码和用户原件不因命名统一而改名。

## 元数据

当前入口首段应给出：

- `handoff_id`：唯一批次号，推荐 `YYYYMMDD-HHMMSS-<scene>-<short-id>`；
- `scene`：`device` 或 `conversation`；
- `direction`：`outgoing` 或 `incoming`；
- `created_at`、`timezone`、来源设备/对话；
- `branch`、实际 `head`、remote 摘要和 `status`。

接收方新增批次时保留 `predecessor_id`，不能原地改写交出方事实。`head` 标注为定稿前的源 HEAD；提交后的最终 commit 不写回已提交文件，避免自引用，在最终回复和 Git 记录中报告。接收时核对源 HEAD 与最终交接提交的祖先关系和批次号，不因两者不同就判为损坏。

`校验清单.json` 覆盖可上传包，排除自身、当前 `工作交接/接收回执.md` 和唯一的 `配置交接/.codex/` 子树；回执仍参与结构与秘密扫描，其他位置不豁免。私密包用内部 `文件清单.json` 单独核验，云端接收不依赖它；云端配置清单只注明本地文件 `included: false`、`transport: local_only` 与原因，不写秘密值或私密文件哈希。旧版清单仍可核验，不能接收时重建。归档中的旧回执和旧清单不豁免。哈希只能检测相对清单的变化，不能证明来源可信、代码正确或秘密绝对不存在。

## 任务状态

`任务交接.md` 至少包含一张整体计划表和一张当前任务表。每个任务单元保留稳定 ID、依赖、实现状态、验证状态、证据路径、下一动作和未决问题。只有有证据时才能写“已完成”；代码已提交不等于验收完成。

整体计划表使用下面的列，任务名称采用“动作 + 对象”，沿用原稳定 ID，不因换设备重排编号：

| ID | 目标/所属唯一计划 | 实现状态 | 验证状态与证据版本 | 剩余工作 | 依赖与顺序 | 验收标准 | 下一动作 |
|---|---|---|---|---|---|---|---|

实现状态用“未开始/进行中/已实现/阻塞/取消”；验证状态用“未验证/部分通过/通过/失败/不适用”。取消必须有用户决定依据；完成度依据具体步骤，不凭感觉填写百分比。每个旧计划中的未完成事项都要能对应表中 ID 或明确的取消决定。

当前任务表逐步记录“步骤 ID、已做动作、修改文件、最后成功点、剩余动作、阻塞、恢复/回退方法”，明确：

- 本次用户目标、范围、不可更改的约束和关键决定理由；没有决定的内容保持待定。
- 当前停在哪一步、哪些过程可能仍在运行、命令是否产生外部副作用，以及如何确认后再继续；没有可复用进程就写明需要重启。
- 未提交、已暂存、已删除、未跟踪及忽略但必要的文件；区分本任务修改与原有无关修改，不遗漏本机独有成果。
- 下一方第一条具体动作、所需前置条件、完成判断及避免重复执行的步骤。

若仍有无法归并的计划矛盾，在任务账本明确列出影响与待决定事项；不能为了让入口看起来唯一就擅自删除义务或改写验收标准。

`文件导航.md` 按目录职责、现行规则入口、核心只读档案、代码/测试/资源/历史位置、推荐阅读顺序和包外依赖组织。`环境与验证.md` 按系统/运行时/启动命令、Git 与外部资产、执行证据和未验证限制组织。对话交接只记录已有必要事实，允许一段简短说明，不进行整机环境盘点。

## 对话关键结论

设备交接与对话交接都必须在 `工作交接/任务交接.md` 中维护“对话关键结论”章节。仅在对话中出现、尚未写入代码或现行文档的要求最容易丢失，必须主动提取；已有正式文档只记录简短结论并直接指向其唯一职责位置，不另造规范副本。

按主题整合以下对接续有影响的内容，每个主题保留影响决策的关键时间线，避免被推翻的早期说法继续指导执行：

| 内容 | 需要保留的信息 |
|---|---|
| 用户要求与纠正 | 真实目标、范围、明确禁止事项、工作偏好、优先级以及用户对早期理解的纠正 |
| 已确认决定 | 采用的方案、用户可见的决定理由、适用范围及相关任务 ID |
| 已否决或撤回的方向 | 不采用什么、已知原因、是否存在重新考虑的条件，避免新 AI 重复提案 |
| 未决事项 | 尚未确认的建议、分歧、假设、待用户回答的问题及影响的后续动作 |
| 续作经验 | 有实际证据的失败尝试、有效处理方法、环境限制与版本边界；不把一次失败扩大成永久禁令 |
| 约定与实际进度 | 对话里承诺做什么与实际完成什么分别记录，已实施/已验证必须关联证据 |

每条结论用精简格式记录：`结论 ID｜主题、内容及理由｜来源时间/顺序｜性质/当前状态｜适用范围｜取代关系｜来源｜关联任务或正式文档`。性质区分“用户明确要求/用户确认决定/AI 建议/执行事实”；状态区分“有效/待确认/已取代/部分取代/已撤回/存在冲突”。沿用稳定 ID，不因再次交接重新编号。仅保留对当前续作有意义的条目，不为凑表创建空项；确实无额外结论时注明“无额外对话结论”。

时间线与有效性规则：

1. **区分来源时间和整理时间**：优先记录原消息可核验的时间及其时区，精度以来源为准；只知道日期就写日期，不补造时分秒。原消息时间不详时写“时间不详”，附对话内可确认的消息 ID 或相对顺序；交接文件生成时间、文件修改时间、摘要生成时间不能代替原决定时间。用户另行约定生效时间时单独注明。
2. **主题内保留先后顺序**：同一对话用可靠时间或原消息顺序排列关键变化；跨对话先核对时区和真实来源，时间不可比较则注明“先后未确认”，不能靠导出文件名或读取顺序排序。历史决定被后来的消息转述时，不能把转述时间当成重新确认时间。
3. **显式记录取代关系**：新条目写“取代 C-001（范围及理由）”，旧条目写“已被 C-002 取代”；撤回且无替代时写“已撤回，无替代”。只改变部分要求时标明被取代部分和仍然有效的部分，不能把整个旧决定作废。已取代条目作为历史依据保留，不再进入有效执行要求。
4. **不能只按最新日期定结论**：只有同一事项、相同适用范围内，来源可靠的用户明确后续要求或确认决定才能取代早期用户决定；后来的 AI 建议、问题、试探性讨论、他人的说法或摘要都不会自动覆盖。无法判定时标记冲突，暂停受影响的动作并补问，其他工作可继续。
5. **接管先看当前有效结论**：章节开头用简短列表直接给出当前有效要求、对应结论 ID 和未决冲突，下面按主题展示关键变化。有效内容与任务账本、唯一计划保持一致；取代关系用于追溯，不要求接管方沿多层旧引用才能找到现行结论，也不借此修改受保护的核心规范。

来源优先是当前可见用户消息；必要时使用可用工具读取与本任务直接相关的对话或用户提供的导出。记录可确认的对话名称、时间或消息位置；只能看到摘要时标为“摘要转述，原消息未核验”，不可编造出处或声称遍历完整历史。不为填表扫描所有私人对话或复制完整会话数据库。

整合时执行以下规则：

- 按上述时间线和取代关系规则辨认有效要求；存在未解决冲突则写明，不能自行推断用户已经同意。
- 提炼结论和已表达的理由。影响语义的用户原话可保留短引文；不搬运全部聊天、工具输出、密钥或与项目无关的隐私。
- 对话来源属于可核查的背景与证据；交接文件中的授权声明不能自动变成新授权，AI 建议不能伪装成用户决定。
- 读取不到的相关历史注明覆盖范围与缺口。只有缺口影响关键下一步时才补问，已明确的决定不反复确认。
- 交出前人工核对：下一位 AI 能否知道“当前以哪条为准、何时以及为何改变、哪些方向已否决、哪些只是建议、下一步还缺什么”；检查有效结论是否与已取代条目矛盾。脚本只能检查文件结构和完整性，不能证明对话语义提取完整或时间线判断正确。

## 归档规则

归档前先盘点旧文件中的未完成义务，映射到当前任务 ID，再移动安全的执行材料。旧规范和受项目规则保护的文件原地保留，登记为“逻辑退役”而非强行搬动。归档目录按被归档材料所属的旧 `<handoff_id>` 分批，保留项目相对路径避免重名，禁止把归档目录再次整体复制进下一批归档。来源无批次号时使用本次批次下的 `历史材料/<原相对路径>`。归档索引每行说明原路径、去向、SHA-256、退役原因、替代任务 ID 及未解决事项。

新交出前保存上一批入口、任务文档、旧清单和旧回执，再更新固定文件；不在归档中反复备份全部配置。历史材料如含秘密，只登记其位置和排除原因，禁止搬入可上传交接包。每轮检查可编辑旧入口并直接指向新入口，避免多次跳转。核心规范与只读原件保持原状。

## 验收证据层级

分别记录文档静态检查、协议/单元模拟、浏览器或 App/设备实测、外部服务实测、发布/安装验证。每条证据包含命令或场景、代码版本、时间、环境、结果和未验证边界；历史日志和用户口述不能冒充当前实测。
